# 0008: Live Buyers and Sellers behind a build switch

Date: 15 Nov 2026 · Status: accepted

## Context
The Buyers and Sellers pages must run on live Toolkit data (AZM-180) without changing the screens, while every other tab stays on demo data and local work and tests need no backend.

## Decision
- `app/api.ts` re-exports the demo module and replaces six functions (`getBuyersUniverse`, `addBuyer`, `updateBuyer`, `getSellersUniverse`, `updateSeller`, `getCurrentUser`) with their live twins when `VITE_DATA=live`. The default is demo.
- The live client is generated by Kubb (types and a fetch client) from the Toolkit's exported OpenAPI spec. `./checks.sh api` and CI fail on drift. Nothing in the client is hand-written.
- Filters, search and order move to the Toolkit. The loader passes the page's URL params as they are; the Toolkit returns `matched`, `total` and the filter options, so `Clear filters (n of total)` still reads the same. The demo functions do the same work so both modes take the same inputs.
- The first 100 rows come from the loader; a "Show more" row fetches the next cursor. Opening a drawer does not reload the list.
- A save waits for the server (`useSaveAction`). A refusal or a half-finished write (Attio saved, Postgres failed) keeps the drawer open with the reason, so it can be retried.
- Phase 3 and 4 actions (Add to deal, New lead, Owner approach) are greyed out in live. Fields with no source column show "Not set" and their edit fields are locked.
- A Cloudflare Worker serves the app and proxies `/api/v1/*` to the Toolkit; Cloudflare Access signs the user in and the Toolkit checks the token.

## Consequences
- Moving to the Phase 0 tables changes the Toolkit's `crm` persistence only.
- `VITE_DATA=live` builds are only useful behind Access, so `engine-dev` flips to live and the demo build is for local work.
