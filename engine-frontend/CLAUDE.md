# Wusool Engine: rules for Claude Code

The Wusool Engine is Wusool Capital's internal operating system for M&A advisors.

- Scope, decisions and requirements: `docs/PRD.md` (source of truth for what to build).
- Look and components: `docs/DESIGN.md` (source of truth for how it looks).
- If the two disagree, or something is unclear, ask Jules before writing code.

## Current phase

A clickable prototype of all 12 tabs on a demo account with invented data, to agree on flow and look with the team. No live integrations.

Build one tab at a time, in this order: Home, Pipeline (with the Deal view), Outreach, Buyers Universe, Sellers Universe, Search (buyers and sellers on one page), Scorecards, Partners, Engine optimization, Multiples, Skills, GitBook link.

After each tab: typecheck, build, click through every flow at 1440px and 390px wide, update the progress log below, open a pull request, then **stop and wait for Jules's feedback** before starting the next tab.

## How to work (Karpathy rules)

1. **Think before coding.** State assumptions and what is unclear before a tab or feature. Ask rather than guess.
2. **Simplicity first.** Build only what the PRD requirement and its check need. No abstraction before its second use. No features the PRD does not ask for.
3. **Surgical changes.** Touch only the files the task needs. Do not reformat or refactor unrelated code.
4. **Goal-driven execution.** Every PRD requirement ends with a check. Make the check pass, then stop.

## Non-negotiables

- **AI never sends.** Every outbound message, record change or document needs a named person's click.
- **3 clicks.** Any action takes 3 clicks or fewer from where its item is shown. Typing does not count; the final Save or Send does.
- **Home in 1 click** from every screen.
- **One layer.** At most one dialog or drawer over a page. A dialog never opens another dialog.
- **No fees on screen-shareable pages.** Fee terms appear only behind an explicit "Show terms" click.
- **No helpers in the product.** No tooltips, tours or "?" bubbles. Labels and buttons must be clear on their own. Exception: a "Build notes" toggle, visible to admins in staging only, for the tech handover.
- **Purposeful interaction.** Pointer cursor and hover effects only on clickable elements. Motion only to show a change of state, off when the user prefers reduced motion.
- **Invented demo data.** No real client names or numbers. A "Demo" badge beside the Engine name says it is a demo account.

## AI usage policy

Code and APIs by default. An LLM only where language must be read or written, and always the smallest model tier that passes the job's test set. Tiers map to Bedrock model IDs in one config file. Never AI for valuations, numbers shown to clients, scoring, fees or sending. A new AI job needs a one-line reason why rules or an API cannot do it. In the prototype, AI output is shown as static demo text marked as an AI draft.

## Design

`docs/DESIGN.md` wins over any design skill (/front-end, /taste may guide craft only).

- Light theme only. Inter only. Navy `#000523` is the single accent. Sky `#C6E1EE` and `#EAF3F8` only for hover, selection, focus and badges, never as text.
- Table style: light header (muted 12px labels on white, one hairline), hairlines between rows, numbers right-aligned in tabular figures. The navy brand header is for client-facing exports only.
- Status never shown by colour alone. Sentence case. No em dashes in UI text. Dates as `12 Mar 2026`, money in USD as `$5.2M` (the Toolkit converts AED from Attio).
- All colours are tokens on `:root`. No new colour without updating DESIGN.md.
- DESIGN.md was written for a single page. Add what the Engine needs (left nav with groups, kanban card, quick-view drawer, phone layout, chart style, activity feed item) to DESIGN.md as you build them.

## Stack (decided)

- React Router 7 in SPA mode for the prototype, TypeScript strict, Vite, plain CSS from the DESIGN.md tokens, Inter self-hosted.
- Hosted on Cloudflare Workers (static assets) at engine-dev.wusoolcapital.com, behind Cloudflare Access (email one-time PIN, @wusoolcapital.com or @dopaminecap.com). Deployed from the monorepo by GitHub Actions (decision 0007).
- Code lives in the `engine-frontend/` folder of the wusool-infra monorepo. Feature branches and pull requests into `dev`; root CLAUDE.md rules (commits, docs, CI) also apply here.
- Production backend (later, built with Raoof): the existing Python Toolkit (FastAPI, AWS eu-central-1 Frankfurt). The front-end calls it through a typed client generated from its OpenAPI schema and never touches a database directly.
- Prototype data lives in one demo data module, shaped so each export can later be swapped for a Toolkit API call. `app/api.ts` re-exports the demo module and swaps in `app/live/api.ts` per function when `VITE_DATA=live`; the live client in `app/gen/` is generated by Kubb from the Toolkit's OpenAPI spec (`./checks.sh api`).

## Code standards (for the tech handover)

The code must be easy to follow for a software engineer and for another LLM.

- Comments explain why, never what. Names carry the what.
- Small components, descriptive names, no dead code.
- A short README per folder once it has more than a few files.
- A one-page decision record in `docs/decisions/` for each major choice.
- Before calling anything done: typecheck and build pass, and the flow was clicked through in a browser.
